# 动手阶段结论 — 数据源探查与方案验证

> 承接 `REPORT.md`。会话已切到完全权限，本节记录**实际探查 API 与验证方案**的结果。
> 结论：**原报告"建议 1"（补 vs-Top-N 列）经证实不可行**，需修正。
> 所有探查为只读；未修改任何项目文件（`crawler.py` 字节数 26676 与探查前一致）。

---

## 一、探查发现：vs-Top-N 数据无法用于 2024/2025 回测

### 1.1 数据确实存在，但口径不对

`/player/stat/detail`（`crawler.py:171`）返回：

```json
"featured_ratings_data": {
  "rating_type": "Rating 3.0",
  "ratings": [
    {"description": "vs top 5 opponents",  "maps": "(18 maps)", "value": "1.36"},
    {"description": "vs top 10 opponents", "maps": "(38 maps)", "value": "1.36"},
    {"description": "vs top 20 opponents", "maps": "(47 maps)", "value": "1.38"},
    {"description": "vs top 30 opponents", "maps": "(47 maps)", "value": "1.38"},
    {"description": "vs top 50 opponents", "maps": "(56 maps)", "value": "1.37"}
  ]
}
```

**三个致命问题：**

1. **不是逐赛事值** — 接口顶层只有
   `basicInfo / featured_ratings_data / player_avg_data / player_stats_data / role_stats_data / teammates`，
   **没有任何逐赛事维度**。模拟器需要的是"每个赛事 × 每个选手"的对手强度，
   而这里只有一串年度聚合标量。
2. **是当前赛季，不是目标年份** — 用权威 id 对照 2025 实际图数：

   | 选手 | 接口图数 | 2025 实际图数 | 判定 |
   |---|---|---|---|
   | ZywOo | 56 | 168 | ✗ 差 3 倍 |
   | donk | 63 | 128 | ✗ |
   | m0NESY | 35 | 152 | ✗ |
   | NiKo | 35 | 166 | ✗ |

   接口返回的是 **2026 当前赛季**的增量数据，对 2024/2025 回测完全不可用。
3. **语义是"对手战队"不是"对手选手"** — `vs top N opponents` 指对阵 top-N **战队**
   时的 rating，与模拟器里"某球员在某赛事的表现"不是同一粒度。

### 1.2 逐图接口也没有对手强度

`/match/getMatchPlayerStats` 的选手条目字段仅：

```
adr, assists, avatar, death, hs, kast, kill, name, playerId, rating, swing, teamId
```

**没有对手排名/强度字段**，无法在采集期自行计算 vs-Top-N。

→ **原「建议 1」不可行。** 该数据既非逐赛事、又非目标年份，无法回填 2024/2025。

## 二、替代方案验证：能否自行构造对手强度？

既然外部数据不可用，测试用**已有字段**（赛事名 + 队伍 + 队伍名次 + 每赛事 Rating）自行构造：

| 可构造信号 | 定义 |
|---|---|
| 赛事内相对 rating | 选手 rating 相对同赛事所有选手的 z-score（加权） |
| 赛事强度 | 该赛事参赛队名次分布的均值 |

**结果（两年一致，均为负）：**

### 2025

| 方案 | Top20 | 头部 MAE | 中段 MAE | 中段 Spearman |
|---|---|---|---|---|
| **现行 v1.2.0** | **18/20** | **0.33** | **4.57** | **+0.336** |
| + 赛事内相对rating ×1 | 16/20 | 1.00 | 6.00 | +0.367 |
| + 赛事内相对rating ×3 | 14/20 | 1.33 | 8.93 | +0.411 |
| + 赛事强度 | 16/20 | 1.67 | 12.07 | +0.244 |

### 2024

| 方案 | Top20 | 头部 MAE | 中段 MAE | 中段 Spearman |
|---|---|---|---|---|
| **现行 v1.2.0** | **17/20** | **1.00** | **5.21** | **+0.213** |
| + 赛事内相对rating ×1 | 16/20 | 1.00 | 5.64 | +0.301 |
| + 赛事内相对rating ×3 | 16/20 | 2.00 | 7.57 | +0.314 |
| + 赛事强度 | 11/20 | 1.33 | 18.36 | +0.512 |

**注意**：中段 Spearman 确实上升（+0.336→+0.411），但 **MAE 和 Top20 重叠同时恶化**。
这是"换了一批人排错"而非"排得更准"，不能采纳。

## 三、分段重排方案（最后尝试，也失败）

思路：**头部完美，那就不动头部**，只对第 7 名之后用中段信号二次排序。

结果（锁定前 6 名，中段用 `现行分 + o×z(平均Rating) + m×z(场次) + r×z(相对Rating)`）：

| 配置 | 2025 中段 MAE / sp | 2024 中段 MAE / sp |
|---|---|---|
| **现行（基准）** | **4.57 / +0.336** | **5.21 / +0.213** |
| o=1, m=1, r=0 | 4.57 / +0.292 | 5.14 / +0.235 |
| o=0.5, m=1, r=0 | 4.57 / +0.292 | 5.21 / +0.235 |
| o=1, m=0.5, r=0 | 4.71 / +0.288 | 5.07 / +0.213 |
| o=1, m=1, r=0.5 | 4.57 / +0.292 | 5.07 / +0.235 |

**没有任何配置能同时改善两年。** MAE 最好持平，Spearman 经常下降。

## 四、修正后的结论

### 4.1 六年/两轮验证的完整负面结果

| # | 尝试 | 结果 |
|---|---|---|
| 1 | 离散 rating 档 → 连续项 | ❌ 几乎无改善 |
| 2 | EVP 分值调整（5/6/4/3 统一） | ❌ 全部更差 |
| 3 | 名次通道缩放（0 ~ 1.5） | ❌ 全部更差 |
| 4 | 年度 z-score 归一化 | ❌ 排序逐位不变 |
| 5 | 补 vs-Top-N 对手强度 | ❌ **数据源不可用**（非逐赛事 + 非目标年）；完美 API 亦不支持年份（见 FINDINGS-4） |
| 6 | 自行构造对手强度/相对 rating | ❌ MAE 与重叠同时恶化 |
| 7 | 分段重排（锁头部，中段换信号） | ❌ 无法同时改善两年 |

**判定：现行 v1.2.0 已经是这个数据 + 这个结构下的最优解。**
中段误差不是缺陷，而是**信息上界**——现有字段不足以区分官方 7–20 名的排序。

### 4.2 这意味着什么

- 中段 Spearman 只有 +0.21 ~ +0.34，而头部是 **+0.71 ~ +0.94**。
  差距不是调参能弥合的，它反映的是**可用信息的多少**。
- 官方中段依赖的两个维度（**对手质量拆分**、**全年聚合稳定性**），
  现有数据源一个都给不出：
  - vs-Top-N：接口只有当前赛季的年度聚合值
  - 稳定性：需要逐月/逐图时间序列，采集侧没有

### 4.3 真正可行的改进方向（需外部数据）

> **更新**：路径 1、2 均已探尽 —— 逐图时间序列已落地但经跨年验证无效
> （`FINDINGS-3.md`），完美 API 不支持按年份取数（`FINDINGS-4.md`）。
> 仅剩 HLTV 人工/代理路线（路径 3）。

按性价比：

1. **HLTV 官方页面抓取** — HLTV 选手页提供逐赛事、逐对手层级的 rating 拆分。
   这是唯一能真正补齐该维度的来源。**实测：Cloudflare JS 挑战 403 +
   国内到 CF 伦敦节点链路不稳定（robots.txt 直接超时）**，纯 HTTP 客户端不可行；
   仅"真实浏览器人工导出"或"代理+自动化"两条路。详见 `FINDINGS-4.md`。
2. **逐图时间序列** — 已实现（`gen_if_data_2025.py` 保留 `series` + 4 个稳定性列），
   但跨年验证双向失败，**不可接入算法**。详见 `FINDINGS-3.md`。
3. 接受现状：把模拟器定位为**顶部 If 线分析工具**（项目原本的判断），
   在 UI 上明确标注中段为参考值。

## 五、建议的工程改动（小、安全、可立即做）

这些是**产品诚实性**问题，不涉及算法风险：

1. **`ADR` / `KPR` 是死字段** — 导入模板、类型、Excel 都有，`score.ts` 从不读取。
   建议：要么接入评分，要么从导入模板移除并在 UI 说明。
2. **`FITTED_WEIGHTS` 预设需加注** — `defaults.ts:65-101` 的注释已说明结构差异，
   但 UI 上"拟合校准"这个标签会让用户以为它更准。实测它中段更差
   （MAE 4.57→5.00，2025）。建议 UI 标注"该预设贴近拟合模型结构，
   不保证中段精度"。
3. **文档补一句信息上界** — 把中段 Spearman 0.21~0.34 与头部 0.71~0.94 的
   对比写进 README/SPEC，说明这不是 bug。

以上 3 项都未执行（用户未指定下一步）。需要的话我可以直接改。
